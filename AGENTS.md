# Harness

A universal, stack-agnostic project setup harness and skill library.

## Project type

A library project. It ships as a reusable package, CLI or archive.

## Commands

| Purpose | Command |
| --- | --- |
| Check | `node tests/run.mjs` |
| Check | `node tests/pilot.mjs` |
| Check | `node web/build.mjs --check` |
| Release | `gh workflow run release.yml -f bump=minor -f summary="..."` |

## Language rules

- All code, identifiers, comments, documentation, commit messages and release
  notes are written in English.
- User-facing strings follow the project's own localization approach. Never
  hardcode a second language in code; keep locales in sync.

## Commits and pushes

- Use short, imperative commit messages in English with a Conventional Commits
  prefix:

  - `feat: short message` - a new feature.
  - `fix: short message` - a bug fix.
  - `refactor: short message` - a change that neither adds a feature nor fixes a
    bug.
  - `chore: short message` - maintenance that does not change behavior.
  - `docs:`, `test:`, `perf:`, `build:`, `ci:`, `style:` - the remaining allowed
    types.

- Keep the subject under 72 characters, lowercase, and without a trailing
  period. Use the body only for context, wrapped at 72 columns.
- Never add AI authorship or co-author trailers: no `Co-Authored-By`, no
  "Generated by ...", no tool, agent or session attribution. The author is the
  human contributor only.
- Stage explicit paths. Never use `git add -A`, `git add .` or
  `git commit -a`. Never stage local planning files, secrets, environment files
  or build output.
- Review the staged diff before committing.
- Run the declared checks before committing. A failing check blocks the commit.
- Do not amend, rebase, squash or force-push existing commits unless the user
  explicitly asks for it.
- Commit and push only when the user asks. When they do, commit the intended changes and push to the current branch.

## Versioning and releases

- Releases are cut through the `Release` GitHub Action
  (`.github/workflows/release.yml`, `workflow_dispatch`). Never create release
  tags by hand.
- Use Semantic Versioning and tag releases as `vX.Y.Z`. Pre-releases use a
  suffix such as `vX.Y.Z-alpha.1`.
- The version comes from the latest `vX.Y.Z` git tag; no file is bumped.
- Choose a bump type (`patch`, `minor`, `major`, `prerelease`, `premajor`,
  `preminor`, `prepatch`) or provide an explicit version.
- Release notes are generated from Conventional Commits since the previous tag
  by `scripts/release-notes.mjs` using `docs/RELEASE_TEMPLATE.md`.
- Pre-release versions contain a hyphen and are published as GitHub
  pre-releases.
- Describe user-visible changes. Do not list commits that are not shipped.
- Never move, delete or reuse an existing release tag. Fix problems with a new
  patch release.
- The first release of a new project is `v0.1.0`.

## CI and build

- Recorded CI depth: `ci`.
- `CI` runs the project checks on ubuntu-latest, windows-latest.
- Checks, in order:

- `node tests/run.mjs`
- `node tests/pilot.mjs`
- `node web/build.mjs --check`
- Run the declared checks before declaring any task done.

## Operating this repository

- This repository is the harness: it configures other repositories and hosts the
  universal skill library. It does not contain application code.
- Follow `setup/SETUP.md` to configure a target repository. It is the only
  supported entry point.
- `setup/decisions.md` is the locked contract. Change it only with the user, and
  update the templates and tests in the same change.
- `setup/questions.md` is the question bank. Keep it in sync with the decisions.
- `templates/` holds deterministic assets; `guidelines/` holds composable
  `AGENTS.md` sections; `skills/` is the skill source of truth.
- After changing templates, guidelines or scripts, run `node tests/run.mjs` and
  `node tests/pilot.mjs`, and keep every test green.
- Never let a template change break rendering for any of the five project types.
- Do not add stack-specific, framework-specific or architecture guidance here.
  Those belong in a future optional skill.
- Keep the renderer deterministic: no timestamps, no environment-dependent
  output, no network calls.

## Skills

This repository is the source of the skill library. Skills live in
`skills/<id>/SKILL.md`; add or change them there and update
`skills/README.md`.

Before a task that matches a skill, read its `SKILL.md` and follow it:

- `commit-and-push` - review, stage explicit files, write a Conventional Commit, commit and push.
- `release-summary` - write a short user-facing summary of the latest release.
- `release-cut` - trigger the release workflow, watch it and verify the result.
- `github-pages` - publish a static site or generated documentation to GitHub Pages.
- `readme` - create, standardize or translate a README.
- `logo` - design a logo system with five versions before creating SVGs.
- `add-skill` - propose a new reusable skill and apply it in the harness repository.

Never include credentials, absolute paths or project-specific details in a skill.

## Secrets and safety

- Never commit secrets, API keys, tokens, credentials, `.env` files, local
  environment configuration, build output or local planning notes.
- Never log secrets, prompts or private data.
- Never force-push and never rewrite published history unless the user
  explicitly requests it on a branch they own.
- Never invent data, sources or dependencies. Verify that a dependency exists
  before using it, and cite the source of any external data.
- Handle errors explicitly. Never fail silently.
- Remove dead code, commented-out code and unused imports before committing.
- Do not add comments that restate the code. Use comments only for non-obvious
  decisions.
